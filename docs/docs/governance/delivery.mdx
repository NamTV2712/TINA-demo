description: "A small delivery process for making and reviewing changes in the self-hosted TINA checkout."
---

TINA uses GitHub for source control and CI. This page records the local development path and the
merge requirements enforced by the repository workflows.

## Before changing code

1. State the user-visible behavior that should change.
2. Inspect the working tree and preserve edits already present.
3. Trace callers and the deployment/configuration paths that use the code.
4. Record a small acceptance check and the relevant documentation surface.

## During implementation

- Change the shared producer when fixing a shared contract; keep client adaptation at client
  boundaries.
- For API, environment, package, or storage changes, update every caller, example, fixture, and
  operator guide in the same change.
- Preserve error handling, validation, security boundaries, and existing license notices.
- Update architecture or contract seals when their underlying inputs change.

## Verification and reporting

Run the focused checks needed for the change when requested or required by the task. Report the
commands, results, and anything left unverified. A passing source test does not establish that a
TINA deployment worked; label runtime behavior as unverified until exercised on the target setup.

## Integration — the merge bar

| Required check | Acceptance |
|---|---|
| Merge bar — value + diff accepted | Runtime PRs need a green `value-fsm` run and `state: value-signed`. Diff is accepted when the author holds the commit bit or a non-author approves the current head. Architecture/security passes and linked-issue acceptance must also pass. |

## Git and release boundaries

Preserve the independent `.git` directory and inherited source history. Keep release receipts and
working artifacts local unless a release owner explicitly selects the artifacts for publication.
